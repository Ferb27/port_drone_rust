## 2. Đề tài mới: tận dụng v3 như thế nào

Thẳng thắn: "port sang Rust" **tự nó không phải đóng góp khoa học**. Reviewer sẽ hỏi "đo được gì mới?". Hướng hợp lý là bản Rust làm **nền tảng**, còn câu hỏi khoa học lấy lại từ v3.

**Tên gợi ý:** *Hệ thống quản lý bầy UAV mở, viết bằng Rust trên nền DroneEngage và ArduPilot, có nhận biết tuổi dữ liệu trong điều phối đội hình.*
(EN: *An Open, Memory-Safe Multi-UAV Management Platform on DroneEngage and ArduPilot with Age-Aware Formation Coordination*)

| Phần của v3 | Dùng lại trong đề tài mới thế nào |
|---|---|
| Mô hình sai số theo tuổi dữ liệu h ≈ τ + T/2 (Bảng 1) | Giữ nguyên làm **lõi khoa học** (Đóng góp 2). |
| Phát hiện về `AP_Follow` 4.7.2 (không bù τ₀) | Giữ nguyên. Node `FOLLOW_TARGET` viết **luôn trong de_mavlink Rust** thay vì node Python riêng. |
| Patch P1 (seq + timestamp trong 6503), P2 (Vector) | Đưa vào de_mavlink Rust thành **tính năng chuẩn**, bật/tắt bằng config (mặc định tắt để giữ B0). |
| Testbed SITL, `delayproxy`, `exp1.py`, `analyze.py`, số đo gate | Giữ nguyên. Số đo B0 cũ là **baseline**, và cũng là bài kiểm tra tương đương cho bản port. |
| RQ1–RQ4, E0–E5, các mốc G1–G4 | RQ1 mở rộng thành "nền tảng Rust chạy ổn trên SITL và 2 drone thật". RQ2–RQ4 giữ. Lịch dời khoảng 4–6 tuần (mục 6). |

**Đóng góp đề xuất:**
1. **Nền tảng** (kỹ thuật): DroneEngage-Rust tương thích ngược, có timestamp/seq, cơ chế latest-wins, cấu hình theo đội hình, bộ cài cho Pi.
2. **Benchmark** (khoa học, giữ từ v3): độ chính xác đội hình theo tuổi dữ liệu, FOLLOW 4.7.2 so với bộ bù.
3. Phụ (tuỳ chọn): đo tài nguyên trên Pi 3B+/Pi 4 khi tăng số UAV. Đây không phải benchmark so với C++, chỉ là số liệu mô tả nền tảng.

**Công trình liên quan phải trích và phân biệt** (tra qua nguồn hợp lệ: arXiv, Google Scholar, trang NXB):
- Aerostack2 (ROS 2, multi-robot aerial): arXiv [2303.18237](https://arxiv.org/abs/2303.18237).
- MRS UAV System (ROS 1, multi-robot); kiến trúc swarm dị thể ROS 2 + PX4: arXiv [2510.27327](https://arxiv.org/html/2510.27327).
- Dronemap Planner (Koubâa et al., Ad Hoc Networks 2019): quản lý drone trên cloud qua MAVLink.
- Škoudlil, Sojka, Hanzálek, ECRTS 2025: ROS 2 viết bằng async Rust đạt real-time tương đương C++, arXiv [2505.21323](https://arxiv.org/abs/2505.21323). Đây là căn cứ học thuật cho việc chọn Rust + tokio.
- Các tài liệu đã có trong v3 (Kilic & Meiboom 2015, Xing et al. TVT 2020, Vera-Amaro et al. 2026, …).
- Chưa tìm thấy bài báo nào của tác giả về DroneEngage. Chỉ có tài liệu kỹ thuật tại cloud.ardupilot.org.

**Cần Ferb quyết:** chốt tên đề tài này, hoặc muốn hướng "quản lý bầy" rộng hơn (giao nhiệm vụ, phân bổ mục tiêu…). Hướng rộng hơn khó kịp SMC 2027.

## 4. Lựa chọn kỹ thuật (Q9)

Nguyên tắc: **dùng cùng stack với server/auth Rust của tác giả** để fork, chép code dễ, và lấy cập nhật về dễ.

| Việc | Chọn | Lý do / ghi chú |
|---|---|---|
| Rust | stable, edition 2021, MSRV ≥ 1.88 | Upstream dùng edition 2021. Crate `mavlink` 0.21 cần ≥ 1.88. WSL hiện có rustc 1.100.0. |
| Async | `tokio` 1 | Upstream dùng. Có nghiên cứu ECRTS 2025 cho thấy async Rust đạt real-time tương đương C++. |
| JSON | `serde_json` **không** bật `preserve_order`, có bật `float_roundtrip` | **Sửa 2026-11-19 (R1):** module C++ dùng `nlohmann::json` thường, object là map đã sắp xếp nên key luôn theo thứ tự chữ cái. `serde_json` mặc định (BTreeMap) cho đúng thứ tự đó. Đã kiểm trên 7191 bản tin ghi được. Server Rust của upstream dùng `preserve_order` là chuyện riêng của server. |
| MAVLink | `mavlink` (rust-mavlink) **0.21**, `default-features = false`, features `std, tokio, transport-udp, transport-direct-serial, dialect-ardupilotmega, mav2-message-extensions` | **Đã thử 2026-11-19 (mục 9).** Đường dẫn module là `mavlink::dialects::ardupilotmega`; phải `use mavlink::AsyncMavConnection`. Crate yêu cầu Rust ≥ 1.88. Nếu thiếu message so với firmware 4.7.2 thì dùng `dialect-dynamic` hoặc `mavlink-bindgen` với XML của ArduPilot. Phương án dự phòng: `mavio`. |
| WebSocket + TLS tới server | `tokio-tungstenite` 0.30, `rustls` 0.23 (ring), `webpki-roots` | Giống hệt server upstream. Bỏ được OpenSSL + Boost. |
| HTTPS tới auth | `reqwest` (rustls, không default features) | Thay libcurl. |
| Log | `tracing` + `tracing-subscriber`, ghi file xoay vòng bằng `tracing-appender` | Thay plog. |
| CLI, lỗi | `clap` 4, `anyhow` + `thiserror` | Phổ biến, ổn định. |
| GPIO | `rppal` | Thay WiringPi, không cần lib C. |
| Hằng số message | Sinh tự động từ `messages.hpp` bằng script, ra `messages.rs` | Tránh gõ tay 2.3k dòng, dễ đồng bộ khi upstream thêm message. |

Các phiên bản trên phải được **kiểm lại bằng `cargo add` vào ngày bắt đầu**, không tin bảng này 100%.

## 5. Hệ điều hành và bộ cài cho Pi (Q3, Q10)

**Hệ điều hành: Raspberry Pi OS Lite 64-bit (Debian 13 Trixie, kernel 6.18)** cho cả Pi 4 và Pi 3B+. Bản này hỗ trợ Pi 3 64-bit, nên chỉ cần build một target `aarch64-unknown-linux-gnu`.

Đã cân nhắc các phương án khác:

| Phương án | Vì sao không chọn (lúc này) |
|---|---|
| DietPi | Nhẹ hơn chút, nhưng cộng đồng nhỏ, dùng cùng kernel. Lợi ích nhỏ, thêm rủi ro. |
| Ubuntu Server | Nặng hơn. Chỉ đáng dùng nếu cần ROS 2, mà đề tài không cần. |
| Yocto / Buildroot | Image tối giản, tái lập tốt, nhưng mất vài tuần học. Để dành cho đồ án. |
| BlueOS | Chạy mọi thứ qua Docker, nặng, hướng ArduSub. |
| Kernel PREEMPT_RT | **Không cần.** Vòng điều khiển chạy trên FC, companion chỉ gửi setpoint ~10 Hz. Nếu sau này cần thì kernel ≥ 6.12 đã có sẵn PREEMPT_RT trong mainline, chỉ cần build lại kernel. |

**Bộ cài: làm theo 2 mức.**
1. **Mức A (làm trong đợt port):** `cargo zigbuild --target aarch64-unknown-linux-gnu` trong WSL, rồi `cargo deb --no-build` ra gói `.deb`, kèm **systemd unit** (thay pm2), có `Restart=on-failure`, `MemoryMax`. Thêm `install.sh`: cài `.deb`, chỉnh sysctl UDP buffer (theo ScriptWiki), cấu hình serial UART cho FC, tạo file config. Xong mức A là cài được lên một Pi OS Lite mới chỉ bằng một lệnh.
2. **Mức B (sau khi lõi ổn):** dựng image bằng **`rpi-image-gen`** (công cụ chính thức, mới hơn pi-gen, cấu hình bằng YAML). Flash thẳng vào thẻ SD là có sẵn DroneEngage-Rust, mạng và UART đã cấu hình.

## 6. Thứ tự port và lịch (Q11)

**Chiến lược kiểm thử chính: so trace.** Trước khi port, chạy stack C++ trên SITL và **ghi lại toàn bộ traffic**: databus giữa module, WSS de_comm ↔ server, MAVLink de_mavlink ↔ FC. Module Rust phải phát ra bản tin tương đương trên cùng kịch bản. Bộ trace này là "đề bài" rõ ràng cho cả Claude và Antigravity.

**Thứ tự:** `de_common` → `de_mavlink` → `de_comm`. Ở mỗi bước, phần còn lại vẫn là C++ (chạy lai), nên luôn có hệ thống chạy được để kiểm tra.
- `de_common` làm trước vì cả hai module kia đều phụ thuộc vào nó.
- `de_mavlink` làm thứ hai vì nó chứa logic swarm, là lõi của đề tài.
- `de_comm` làm cuối vì giao tiếp với server và auth, cần khớp với server Rust đã có.

## 9. Nhật ký R0

**2026-11-19: kế hoạch được Ferb duyệt.**

Môi trường build (WSL Ubuntu 22.04 trên máy GTR, 16 nhân, 22 GB RAM):
- Có sẵn rustup 1.29.3, rustc/cargo 1.100.0.
- Đã thêm target `aarch64-unknown-linux-gnu`.
- Đã cài zig 0.17.1 (qua `pip install --user ziglang`), `cargo-zigbuild` 0.24.1, `cargo-deb` 3.8.0.
- Lưu ý: WSL đang chạy **kernel tự build cho Android** (`.wslconfig`: `kernel=...bzImage-adsspeed`, `ibt=off`). Đây có thể là nguyên nhân WSL từng restart khi chạy `cargo test`. Nên giữ `-j 4` khi build/test.

Thử crate `mavlink` (thư mục `~/spike/mav` trong WSL):
- Bản mới nhất là **0.21.0**, không phải 0.18 như lúc research.
